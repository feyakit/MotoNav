# 2.16 firmware review and limits

Base: `adapt-216` at `83b4390`; development continues on `feature/byd-bms`. This is a focused review of the listed paths, not a claim that all firmware behavior has been proven correct.

- Display: `boards/216/MotoNav/MotoNav.ino` creates a CO5300 over ESP32 QSPI and an Arduino_GFX framebuffer, with PSRAM double buffers and asynchronous flush. `pin_config.h` provides the 480×480 2.16 board configuration. Normal and cardinal rotation send the full square framebuffer. Free rotation and page transition code previously used circular spans; this change uses full-width destination spans. Rotated source pixels outside the square are still black, as expected. Physical panel orientation, controller timing, tearing and touch alignment have not been verified here.
- Touch: CST92xx on I2C, interrupt-driven polling; point and gesture vectors share `touchVectorToCanvas` with board flips and rotation. Screen interactions are applied on release. The new menu and BMS controls use this path; simultaneous navigation, scrolling, phone calls and rotation need hardware testing.
- Phone/navigation: the firmware retains its existing encrypted BLE peripheral, RX queue, message parser, bitmap text, map/raster rendering and dirty-frame pipeline. The square UI adds navigation MENU/SOC shortcuts; it does not replace the existing map renderer with the reference image. The map renderer and some navigation artwork still contain circular layout assumptions and have not been fully redesigned for a square screen. Phone data, not preview data, remains the source for navigation/speed/trip values.
- Music: the existing HID/AMS and app control paths remain in use. The touch hit locations were moved with the buttons. Phone-provided text images are fitted to bounded rows. The protocol does not currently provide a usable album-cover image here, so the page says `NO COVER`; progress is shown only when AMS provides valid timing. Volume control is not invented. Hardware media-control and gesture regression testing remains required.
- BLE: the phone server and Apple Media client's custom GAP handler remain in place. `BmsScan` uses a separate NimBLE callback and bounded queues; passive scan results are kept in at most six entries, four visible per page. Non-ASCII advertisement names are currently replaced with `?` for the bitmap font; the raw advertisement bytes remain in serial logs. An explicitly selected address connects; discovery and diagnostic notify/indicate subscription are asynchronous. Only an explicitly selected characteristic's standard CCCD can be written; no unknown BMS command is sent. Notification logging truncates above 128 bytes and reports queue drops. Reconnection uses an in-RAM address and requires manual resubscription after rediscovery. The ESP32-S3 3.3.10 library configuration allows three connections, but this is not proof of simultaneous phone/BMS reliability or performance. No RF, heap-leak, pairing or long-running measurements exist yet.
- BMS: field-level validity flags include SOC, voltage, current, temperature, cell values, capacity, cycles, SOH and alarms. The protocol decoder intentionally rejects unknown packets. Connection transitions invalidate prior measurements. The default build shows missing/stale values as `--`; the simulation build is conspicuously marked. A single timestamp currently represents the sample, not individual field timestamps.
- Power: the existing five-minute no-navigation shutdown remains. Longer BLE-only tests must account for it; it has not been redesigned.

The reference mockup contains six square pages. Battery summary/cells, menu and BLE page use shared firmware drawing functions and have host raster previews; host rasterization approximates Arduino_GFX and is not a device framebuffer capture. Navigation and music now include square-oriented changes but have no trustworthy complete 480×480 screenshots or three-round visual reviews. Their remaining typography, artwork, square map layout, status bar and visual equivalence are not complete. There is no proof that physical interaction works, and settings currently directs users to existing phone controls rather than inventing settings.

Current 2.16 default build with ESP32 Arduino core 3.3.10 succeeded: application 1,289,319 / 3,145,728 bytes; static RAM 89,308 / 327,680 bytes. This does not measure runtime heap, PSRAM fragmentation or BLE coexistence. Host C++ data, UI, advertisement, media and rotation tests, idle timer C test, and five Python flasher tests passed. Existing deprecated touch-header warning remains; no hardware test or flash was performed.

The separate `MOTONAV_BMS_SIMULATION=1` 2.16 build also succeeded: application 1,289,363 / 3,145,728 bytes; static RAM 89,308 / 327,680 bytes. Both builds were made with Arduino CLI and ESP32 core 3.3.10; see `firmware/BMS_PROGRESS.md` for build and manual test instructions.
